# 受信側への依頼: 戻り `rt` の URL 露出対策

対象: Jump から `302 Location: <受信 URL>?rt=<JWS>` で戻りトークンを受け取る
Rails の各受信アプリ。

## 背景

2026-11-14 に OWASP ASVS 5.0.0 の観点で Jump をレビューした。その結果、
V14.2.1（機密データを URL のクエリに載せない）に関わる残存リスクは、
Jump への入力 URL と受信側への出力 URL の両方にある。
JWS は暗号化ではなく署名であり、payload 内の遷移先 URL やクエリ値も読み取れる。

Jump 側では次の対策が済んでいる。

- `Referrer-Policy: no-referrer`、`Cache-Control: no-store`
- プラットフォームログのクエリ文字列 redact（`redact_query_string`）
- 自前ログから `rt` と JWT 形状の値を除去

一方、戻りの `rt` は受信側の URL に載って届く。
そのため受信側のページで次の経路から漏れうる。

- `Referer` ヘッダ（受信ページから外部リソースや外部リンクへ送られる）
- 受信側のアクセスログ、APM、エラートラッカー
- ブラウザ履歴、ブックマーク、共有された URL
- 受信ページに読み込まれたサードパーティスクリプト（`location.href` を読める）

`rt` の有効期限は 30 秒で、`rpl: reuse` のため Jump 側ではリプレイを
検出しない（ADR 0002）。漏れた `rt` は、期限内であれば第三者が再利用できる。
保存領域を利用できないため、この再利用は所有者の受容リスクとする
（[ADR 0010](../adr/0010-accept-stateless-token-reuse.md)）。
再利用を拒否するストレージや `jti` の一回消費を必須にはしない。
これは機密情報の URL 露出を解消したという判定ではない。

発行側でも、遷移先 URL にパスワード、セッション・アクセス・リフレッシュ
トークン、秘密鍵、不要な個人情報を含めない。必要な OAuth パラメーターは
発行側と受信側のログ、APM、エラートラッカーでも保護する。

## 依頼事項

1. `rt` を受け取るアクションは、検証直後に `rt` を除いた URL へ 303 または 302
   でリダイレクトする。HTML を `rt` 付き URL のまま描画しない。
2. 上記のアクションの応答には `Referrer-Policy: no-referrer` と
   `Cache-Control: no-store` を付ける。
3. Rails の `filter_parameters` に `rt` を加える。リバースプロキシ、APM、
   エラートラッカーのログでもクエリの `rt` をマスクする。
4. 認証、認可、CSRF、OAuth の state・nonce・PKCE を操作ごとに検証する。
   Jump のトークンだけでログインや副作用を許可しない。
   入力 `rt` を再利用すると新しい戻り `jti` が発行されるため、
   戻り `jti` の一回消費だけでは操作全体の再実行を防げない。
   一回限りの実行が必要な操作は、受信側で別途その保証を設計する。
5. 検証時に `iss` が Jump の origin であること、`aud` が自 origin と一致する
   ことを確認する。protected header の `typ` は `docs/receiver-contract.md`
   のとおり完全一致で検証する。

## 確認方法（受信側）

- `rt` 付き URL へアクセスすると、本文を返さずに `rt` なしの URL へ
  リダイレクトされること
- `rt` を再利用しても操作固有の認証・認可・CSRF・OAuth 検証を省略しないこと
- ログに `rt` の値が残らないこと

これらは受信側への依頼であり、このリポジトリで実装や本番動作を確認した
ものではない。URL を除去しても、既に記録されたログやブラウザ履歴を
消せるわけではない。
