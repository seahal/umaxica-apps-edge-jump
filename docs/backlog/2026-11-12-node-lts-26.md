# Move Node.js from 24 to the Newest LTS Line (26) (2026-11-12)

Owner: Jump. Status: queued.

## Current Node.js 24 pins (observed 2026-11-12)

- `package.json` `engines.node` (`24.21.0`)

## Policy (owner, 2026-11-12)

Follow the newest Node.js LTS line and keep moving with it; do not freeze on an exact version.
Pinning one patch release for long leaves the project behind on fixes and makes the next jump bigger.

- Target now: Node.js 26 LTS (LTS since 2026-10-28; Active support until 2027-10-27, security
  support until 2029-04-30). Node.js 24 left Active support on 2026-10-20.
- Declare the major line where a tool accepts it (for example `.node-version` `26`, `engines.node`
  `>=26 <27`, container base `node:26-<distro>`), and let automated dependency updates
  (Dependabot or Renovate) move patch and minor versions. Where a tool requires an exact version,
  update it routinely to the newest 26.x instead of leaving it fixed.
- Move to the next LTS line when it becomes LTS (Node.js 27 is planned for April 2027 and LTS in
  October 2027 under the new release model); record the change here.
- Keep every place in a repository on the same line (local version file, `package.json` engines,
  container images, CI workflows, devcontainer).
- Check the toolchain on the new line before switching (Vite, Vitest, oxlint/oxfmt, Wrangler, native
  npm modules) and record the result in `evidence/` where the repository keeps one.
- Best done when the development containers are rebuilt.
