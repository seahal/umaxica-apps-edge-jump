# PaaS の障害・制約による動作不良

Cloudflare Workers などの PaaS 側の障害、サービスの制約、依存サービスの
応答不良により、Jump が正常に動作しない可能性がある。
アプリケーションのコードが正常でも、常に処理の成功を保証できるわけではない。
これは想定する運用上の可能性であり、現在の障害を確認した記録ではない。

## レート制限の呼び出しが失敗した場合

Cloudflare Workers の Rate Limiting バインディングの呼び出しが例外で失敗した場合、
Jump は `jump_rate_limit_skipped`、`reason=limiter_call_exception` を記録し、
レート制限を適用せず処理を続ける。この間に負荷抑制が弱まるリスクは
[ADR 0009](../../adr/0009-accept-rate-limiter-fail-open.md) で受容済み。
署名・クレーム・転送先の検証は引き続き行う。

通常の制限超過は 429 で拒否する。バインディングの欠落や不正な応答、
クライアント IP の欠落・不正、リクエスト期限切れまで許容する判断ではない。
また、Workers 自体の CPU・実行時間などの制約を回避するものでもない。

## 確認手順

1. 発生時刻、HTTP ステータス、`X-Request-ID` と安全な診断ログを確認する。
   `rt`、完全なリクエスト URL、秘密鍵・秘密値を記録しない。
2. Cloudflare の障害情報と Workers のエラー・リソース状況を確認する。
   例外が発生しただけで PaaS 側の障害と断定しない。
3. `jump_rate_limit_skipped` の発生状況とリクエスト負荷を確認する。
   通常の 429 と、制限呼び出しの例外を区別する。
4. 配備バージョン、必要なバインディング・設定、発行者 JWKS の応答を確認する。
   秘密値をログや報告へ出さない。
5. 復旧後、通常の遷移とレート制限が期待どおりに動作することを確認し、
   実際に観測した結果を `evidence/` に記録する。
