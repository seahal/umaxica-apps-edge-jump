# Rails の RT 検証における JWKS 過剰再取得の上申レポート

作成日：2026-10-11（JST）
対応管理ID：RAILS-JWKS-P0（ローカルの対応依頼ID。外部チケットは未作成）
優先度：P0（依頼者指定の対応優先度。CVSS Criticalや本番侵害を意味しない）
担当範囲：Rails受信側と、その入口を保護するインフラ
状態：未修正。コード上の制御不足を確認し、実環境での負荷影響は未測定。

## 上申する判断

RailsがRedirect Token（RT）を検証する際、署名が無効な入力でも公開鍵セット（JWKS）の取得を繰り返せる経路がある。
未知の鍵識別子 `kid` を毎回変更すると、識別子ごとの負キャッシュを回避して共有JWKSキャッシュを削除し、再取得に進む。
確認したコントローラーでは、この処理が通常のレート制限より前に配置されている。

Rails担当者とインフラ担当者によるP0調査、修正、受け入れ試験の実施を要請する。
Jump 0.4.0のパス対策とは独立したリリース阻害要因として管理し、対応または同等の防御の実証まで全体の安全性を承認しない。
本レポート作成時点で認証突破、データ漏えい、サービス停止、本番への攻撃は確認していない。

## システム上の発生箇所

通常の転送は「Rails発行側 → Jump → Rails受信側」の順で行われる。
Jumpは発行者の署名と転送先を検証し、新しい署名付きRTを付けてRailsへ遷移させる。
Rails受信側は、そのRTをJumpの公開鍵で独立に検証する。

今回の入力はRails受信側へ直接送信できるため、Jumpを通過する必要がない。
Jumpのレート制限や有効な発行者署名は、この入口への負荷を防ぐ条件にはならない。
対象Railsのホストとルートに到達できることが攻撃条件となり、認証や先行middlewareの影響は実ルートで検証する必要がある。

```text
到達可能なRails受信ルートへ GET ?rt=<形式上はJWTの偽トークン>
  → JWTヘッダーから未検証のkidを取得
  → キャッシュされた公開鍵セットにkidが存在しない
  → 共有JWKSキャッシュを削除してネットワーク取得
  → 鍵が見つからず拒否
  → 400を描画して処理終了
     後段の通常レート制限はこの取得処理を保護できない
```

## 確認したコードと証拠の強さ

確認対象は隣接する `umaxica-apps-global` のHEAD `2a1644f73238839ed7ed513bd4681ea393a86682` である。
監査時、受信verifier、URL value、JWT codec、受信concernの4ファイルに未コミット変更はなかった。
根拠の詳細は [ASVS監査記録](../../evidence/2026-10-11-asvs-jump-rails-audit.md) に保存している。
以下の行番号はこの監査時点のコードを指す。

| 同ファイル `:121-129`                                           | 強制取得時に共有キャッシュを削除し、fetcherを呼ぶ。取得先単位のcooldownと同時取得の集約がない。 |

**コード確認済み**：処理順序、未知kidでの強制取得、共有キャッシュ削除、kid単位の負キャッシュ。
**未実証**：実稼働環境での取得件数、同時接続数、停止に至るリクエスト量、全surfaceの到達可能性、WAFを含む有効な制限。
RailsコンテナはPodmanのread-only runtimeエラーで利用できず、Rails統合試験も負荷試験も実行していない。

## 発生させる入力の条件

無作為な文字列は、JWTとして解析できず早期に拒否される。
問題の処理へ到達するには、Base64URLの3部分からなるcompact JWTとして解析できる入力を用い、ヘッダーの必須条件を満たす必要がある。
監査対象codecの条件に合わせると、ヘッダーは次の形となる。

```json
{ "typ": "JWT", "alg": "ES384", "kid": "unknown-key-0001" }
```

payloadは解析可能なJSON object、署名部分は形式上解析できる無効な値とする。
正常な署名や本番秘密鍵は不要である。
未知のkidでは、署名を検証する鍵を探す段階で取得が発生し、その後に拒否されるためである。
実際にどの入力がJWTライブラリの事前解析を通るかも、後続の実行試験で固定する。

| 送信するkid             | キャッシュが正常で、先行制御を通った場合のコード上の動作 |
| ----------------------- | -------------------------------------------------------- |
| `unknown-key-0001`      | 該当鍵がなく強制取得し、拒否する。                       |
| 同じ `unknown-key-0001` | 負キャッシュの有効期間内は取得を省略できる。             |
| `unknown-key-0002`      | 負キャッシュのキーが変わり、再取得に進む。               |
| `unknown-key-0003`      | 再取得に進む。                                           |

これはコードから導いた発生手順であり、実行済みの攻撃ログではない。
JWKSの取得先は設定済みJumpに固定されるため、任意URLへのSSRF成立を主張するものでもない。

## 想定される影響

受信RTを最後に拒否しても、Railsはそれまでにネットワーク通信とキャッシュ操作を行う。
多数の異なるkidを処理すると、Railsのリクエスト処理枠や外向き接続、JWKS提供側の割当を消費し、正当な利用者の処理遅延や失敗につながる可能性がある。
共有キャッシュの削除と同時取得が重なると、有効なRTの鍵取得にも影響する可能性がある。

先行する認証、CloudflareやWAFの制限、ネットワーク隔離は影響を抑え得る。
ただし、それらの有無と対象ルートへの適用状況は今回確認できていない。
重篤度を確定するには、実際の入口の到達可能性と取得回数の測定が必要である。
P0は対応順序を示し、未測定の可用性影響をCriticalと断定する数値評価ではない。

## 要求する修正と受け入れ条件

1. RTの解析とJWKS取得より前に、受信入口の負荷制限を置く。
   RTの成功時も失敗時も制限対象とし、制限超過時はネットワーク取得を行わない。
2. 再取得をkidごとではなく、設定済みJWKS取得先ごとに制御する。
   未知kidを変更しても取得間隔の制限を回避できないことを試験する。
3. 同じ取得先への同時取得を集約する。
   複数プロセスや複数インスタンスでの許容取得数も明示する。
4. 未知kidだけを理由に、まだ有効な共有鍵セットを削除しない。
   新しい鍵セットを検証した後に置換し、期限切れや失効済み鍵を無条件に利用する実装にしない。
5. 負キャッシュに件数と寿命の上限を設ける。
   kidを増やすだけでエントリー数を増やし続けられないことを確認する。
6. 事前公開を含む通常ローテーション、緊急失効、取得障害、壊れたJWKSの拒否を回帰試験する。
   Jumpの署名、URL結び付き、30秒TTL、state等の検証を維持する。

安全な再現試験は、隔離したRails環境、非本番鍵、取得件数を数えられるstub JWKSで行う。
正常鍵のキャッシュを温めた後、同じ未知kidと複数の異なる未知kidを小さな固定件数で送り、HTTP応答、fetch回数、キャッシュ削除回数を比較する。
同時実行と取得障害も別ケースとして試験し、各ケースの許容取得数を先に定義する。
実トークンや秘密鍵をログへ出さず、本番へ負荷をかける試験はこの依頼に含めない。

## Jumpのパス改修との関係

Jumpで確認した `/sign/out.html/` の拒否回避は、転送先のパス解釈に関する別件である。
その修正は [パス境界設計](jump-0-4-path-boundary-design.md) と [改修検証記録](../../evidence/2026-10-11-path-boundary-remediation.md) で管理する。
Jumpを改修しても、Railsへ直接届く偽RTの処理は変わらない。
本依頼ではRailsのコード、設定、鍵、デプロイを変更していない。

## 完了の判断に必要な証跡

Rails担当者は、修正候補のcommit SHA、到達可能な受信ルート、callback順序、取得回数の単体試験と統合試験を提出する。
インフラ担当者は、先行する制限の適用箇所と偽RTにも有効なことを確認する。
正常なJumpからの受信、URL比較、鍵ローテーション、緊急失効、障害時拒否を含めて審査し、リリース判断を更新する。
